# Supabase account backend

Apply migrations/202609080001_account_service.sql to the existing project, then deploy functions/codevalanche-account with gateway verify_jwt=false. The handler always verifies the Bearer token using the project Auth server, checks its subject and session_id against a service-role-only auth.sessions read, and rejects app-blocked/revoked sessions. Secrets SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY are supplied by the Edge runtime; never ship the service key in clients.

GET returns get-account; POST accepts JSON {action,...}. Exact production origins are codevalanche.com, www.codevalanche.com, account.codevalanche.com; native clients may omit Origin. Browsers cannot use arbitrary origins. Body limit 16 KiB. After authentication every action body is checked against its schema in functions/codevalanche-account/schemas.mjs before the action runs (field types, enums, lengths, no control characters; unknown extra fields are ignored for older clients). A new action must add its schema; supabase/tests/schemas.test.mjs fails otherwise. authenticated rate limit 60/min/user, feedback 3/min/user. Auth itself supplies sign-in abuse controls. Rate-limit buckets are per user, not attacker-provided IDs.

Actions: get-account; update-profile {displayName?,bio?}; sign-out-others; revoke-session {sessionId}; request-deletion {confirmation:'DELETE'}; cancel-deletion; consent {analytics:boolean}; feedback {category:'bug'|'idea'|'general',message}; event {eventId:UUID,eventName:'website_view'|'download_clicked'|'app_opened',platform,consent:true}. Events currently require an authenticated user and stored consent. Anonymous website analytics are intentionally not accepted by this endpoint.

get-account includes user {id,email,displayName,bio,emailVerified}, identities in signInMethods, sessions {id,createdAt,lastSeenAt,userAgent,current}, deletion {scheduledFor,status:'pending'} or null, analyticsConsent. Desktop aliases: id, userId, sub, session_id, email, email_verified, display_name, name.

Administrators require server-owned auth.users.raw_app_meta_data.codevalanche_admin=true. User metadata never grants privileges. Admin actions: admin-list-users {page?} (50/page), admin-block-user / admin-unblock-user {userId}, admin-feedback (latest 100), admin-analytics (latest 1000 event rows, explicitly bounded rather than an all-time total). Provision an administrator only through trusted Supabase administration. Self-blocking is refused. No administrator credentials are in the website or desktop.

All application tables have RLS enabled and no anon/authenticated grants or policies: clients cannot bypass the live-session and actor checks by using PostgREST directly. Service role performs the actor-scoped operations. Auth schema is read only through the narrowly scoped RPC; no trigger or mutation of auth internals is installed. Single-session revocation denies this application immediately; it does not terminate that refresh token at the Auth service. Sign-out-others uses Supabase Auth's official revocation API.

Deletion is a recorded request with a 30-day grace date and cancellation. No purge scheduler is installed, and the service does not promise automatic deletion. A reviewed retention policy and verified purge job must be added before automatic deletion is advertised. Analytics and feedback history are currently bounded per response, with no scheduled retention cleanup. No paid service is required.

Validation: node --test supabase/tests/*.test.mjs (Node 24); npx deno check --node-modules-dir=auto supabase/functions/codevalanche-account/index.ts. Handler security tests mock the service boundary; live migration execution, live auth/session revocation and RLS smoke tests remain deployment checks.

Sources: https://supabase.com/docs/guides/auth/sessions (session_id vs auth.sessions), https://supabase.com/docs/reference/javascript/auth-admin-signout (official others scope), https://supabase.com/docs/guides/auth/managing-user-data (JWT invalidation and Auth user management).

Live security smoke (operator only): set SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY and SUPABASE_SERVICE_ROLE_KEY in the process environment, then run `node supabase/scripts/live-security-smoke.mjs`. It creates three marked example.test users with email_confirm:true, tests actual account/session boundaries, then deletes only fixtures whose UUID, email and marker still match. This bypasses email delivery solely for integration fixtures and does not validate signup email. Output contains check labels and cleanup status only; no credentials persist. Cleanup failures report fixture UUIDs for operator deletion. No keep-user option is implemented. The function must include sign-out-current (official Auth local-scope revocation) before running this version.

Configuration in the repo: `supabase/config.toml` (no secrets; every secret is `env(...)`) holds the Auth settings: 12-character minimum for new passwords, Cloudflare Turnstile CAPTCHA (off until the operator sets `SUPABASE_AUTH_CAPTCHA_SECRET`, the site key in `src/config.js`, and enables it), the redirect URLs and the translated email templates in `supabase/templates/` (English and Romanian, picked from the user's metadata `locale` that the account page sets at sign-up). Edit `supabase/templates/email-templates.mjs`, then run `node supabase/templates/email-templates.mjs`; `supabase/tests/config.test.mjs` fails if the HTML drifts. Production changes stay an operator step: `supabase link`, compare, then `supabase config push` and read its diff before confirming.

Two-step verification (migration `202610160301_mfa_recovery_admin_audit_session_cut.sql`, `functions/codevalanche-account/mfa.mjs`): the authenticator is Supabase Auth MFA (TOTP, `[auth.mfa.totp]` in config.toml); the account page enrols it with supabase-js and verifies a code, which raises the session to aal2. For a user with a verified authenticator the function answers only aal2 sessions (401 `{error:'MFA required', mfaRequired:true}` otherwise), except `sign-out-current` and `mfa-recovery-redeem`. Recovery codes are the function's own: `mfa-recovery-codes` (aal2 only) returns 10 new codes once and stores only SHA-256 of "user id:code" in `codevalanche_mfa_recovery_codes` (service-only, RLS); `mfa-recovery-redeem {code}` (5 tries/min/user) uses one code once and removes the user's TOTP factors through the Auth admin API, so a user who lost the phone signs in with password + code and can turn the authenticator on again; `mfa-disable {factorId}` (aal2 only) removes the factor and the codes. `get-account` adds `mfa {enabled, factors[{id,friendlyName,createdAt}], recoveryCodesRemaining}`. Tokens issued to an OAuth client (claim `client_id`, the desktop app) are held to aal2 only when the function secret `CODEVALANCHE_MFA_ENFORCE_OAUTH_AAL2=true` is set; set it after checking that such a token carries `aal2` for a user who passed the authenticator on the consent page (the consent page asks for it before approving). Supabase Auth also has experimental native recovery codes (`auth.mfa.recoveryCodes`, client flag `experimental.recoveryCodes`); they are not used while experimental.

Administrator journal: every admin-list-users, admin-feedback and admin-analytics read and every block/unblock writes a row to `codevalanche_admin_access_log` (actor, action, target, row count, time; the service can insert and read, never update or delete). If the row cannot be written, nothing is returned (503). Block also cuts every session: after the Auth ban, `codevalanche_revoke_all_sessions` marks all the user's sessions revoked for this function, then deletes their Auth sessions and refresh tokens, so no refresh can mint a new token and a later unblock does not revive old sessions. The answer reports `sessions {appRevoked, authSessionsDeleted, refreshTokensDeleted, authRevoked}`; `authRevoked:false` means the database refused the Auth delete and only the ban and the function's own refusal hold. An access token already issued stays cryptographically valid until it expires (at most `jwt_expiry` = 1 h) but this function refuses it at once; nothing else accepts these tokens (no anon/authenticated grants, no Realtime).
