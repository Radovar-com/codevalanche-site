# Account security qualification

The additive v2 code is local implementation. Before rollout, the operator must provide separate staging receipts for database privileges, current Auth schema, OAuth clients and `aal2`/`amr` propagation, direct provider endpoints, CAPTCHA, SMTP, and recovery in another browser. No production changes are made by these scripts.

`supabase/scripts/auth-policy.json` is desired configuration, not a provider snapshot. Run `verify-auth-policy.mjs` on a sanitized actual snapshot; its output contains missing controls only. Recovery expiry is 900 seconds, new passwords at least 12 Unicode characters (same as `minimum_password_length` in supabase/config.toml), exact HTTPS callbacks, distinct desktop/iOS/Android clients, and provider CAPTCHA. A frontend challenge or gateway rate limit cannot protect direct Auth requests. Keep refresh capacity separate from password ceilings. Failed password attempts never suspend accounts or revoke legitimate sessions.

Provider MFA/password verification hooks may require a plan capability. Do not purchase or enable them automatically. Record missing capability in the coverage report. No hook inference can substitute for successful provider session creation.

Recovery uses provider `verifyOtp({type:'recovery',token_hash})` with explicit exchange after navigation; remove callback secrets from history before network exchange. Email template must send to the exact account route with `token_hash`/`type`. Keep PKCE for ordinary OAuth/code callbacks. Qualify link expiry, reuse, mail scanner prefetch, and different browsers with actual staging email. Never log callback URLs, OTP codes, passwords, tokens or bodies. Configure production SMTP and prove actual delivery separately.

`auth.users` password changes and `auth.mfa_factors` changes update a server credential stamp and policy version through restricted triggers. Password changes withdraw existing application sessions. Recovery does not clear suspension or grant remote authority. OTP/invite/signup/magic-link sessions are conservatively restricted until fresh password/OAuth authentication because provider AMR does not reliably distinguish recovery OTP. This also restricts ordinary passwordless sessions; expand only after provider qualification establishes an authoritative recovery-purpose binding.

MFA freshness uses the verified MFA `amr.timestamp`, current verified factor count, and the provider change stamp; refresh `iat` is never freshness evidence. A factor change at the same second as verification requires a later challenge. Missing evidence denies sensitive actions. Direct provider factor changes must be tested in staging. Lost factors require an alternate verified factor or an operator-reviewed recovery process; access to email alone cannot remove MFA. Guest local remains available.

Rollback disables new online/remote admissions, keeps the additive schema, and preserves local data. No worker is scheduled or production configuration changed by these files.

Application migration never merges Keycloak/Supabase cohorts or canonical user UUIDs by email. This is distinct from provider identity linking: Supabase can automatically attach an OAuth identity with a matching verified email to the same Auth user UUID. The manual-linking setting does not disable automatic provider linking. Do not delete identities or add speculative hooks to change that behavior. Staging qualification must cover matching verified/unverified emails, existing password plus Google, Google-only password setup, and recovery after linking. Sign-in methods shown by the UI come from current provider identities. [Provider identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).

Temporary bans carry a monotonic suspension generation. Expiry jobs compare that generation and canonical deadline before completing; old jobs cannot relax a later ban. The worker reads authoritative current Auth ban status and never sends an old timed-expiry `ban_duration:none`, avoiding a delayed unban overwriting a newer provider ban. Provider outage or an active provider ban leaves expiry pending. Completion increments policy version and retains session/grant withdrawal. Due expiry is reconciled on verified account-policy reads and through the maintenance worker; the owner must qualify its schedule and alerts before release.

Maintenance source is `account-maintenance-dispatcher`, with a closed PostgreSQL due-job selector and at most 10 jobs per invocation. Existing operation/erasure/outbox leases prevent concurrent claim, and retry selection respects backoff and delivery deadlines. No variable UUID is needed in the scheduler request. `ACCOUNT_DISPATCHER_ENABLED` defaults off; erasure needs its separate qualification flag. The operator configures an authenticated HTTPS POST every 15–60 seconds and a separate daily retention call, then records successful retry/crash, pending/dead-letter alert and provider receipts. `verify-maintenance-config.mjs` checks a sanitized actual configuration receipt; it does not configure the scheduler or turn desired settings into proof.

Worker database roles are NOLOGIN and receive only their necessary EXECUTE capabilities. The selector has its own reader role, and each dispatched task uses a separate role-token adapter. PostgREST must verify the owner-supplied signed worker token and its role; the adapter checks an invoker capability RPC and refuses role mismatch. It never falls back to service_role. The owner configures these tokens, their lifetime and rotation; this code does not mint or inspect signing keys. Notifier, audit importer and retention use only a public API key plus their worker Authorization token and never request an Auth admin credential. Ban reconciliation and Auth erasure necessarily use a separate server-only Auth admin key: Supabase's Auth admin credential remains broad at the provider, so process isolation and endpoint capability checks are required. A JavaScript role variable cannot restrict that provider key.

If a separately suspended user cannot get a fresh provider session, self cancellation is not claimed reachable. `admin.deletion.cancel` offers an audited owner/accounts_admin path with verified current session, MFA within five minutes, reason and bound operation ID before purge. Cancellation restores the separate suspension; it never unbans the user or restores withdrawn grants. The self route still requires exact getUser validation, current session membership, recent primary authentication and enrolled MFA. Qualify banned-user recovery/login behavior in staging instead of bypassing provider checks.

Factor verification may update the provider stamp during the same second as the AMR claim. The server deliberately refuses that token for sensitive access rather than rounding the stamp down. First enrollment tells the user to perform a distinct later verification with a new code. SQL + principal/assurance boundary tests cover same-second refusal and later verified challenge; actual GoTrue ordering and OAuth propagation remain staging gates.

Primary references: [JWT claims](https://supabase.com/docs/guides/auth/jwt-fields), [OAuth token security](https://supabase.com/docs/guides/auth/oauth-server/token-security), [MFA](https://supabase.com/docs/guides/auth/auth-mfa), [hooks](https://supabase.com/docs/guides/auth/auth-hooks), [password security](https://supabase.com/docs/guides/auth/password-security).

Native outcome ingestion is a separate machine endpoint, `account-native-ledger`, with gateway user-JWT validation disabled only for this endpoint so its own dedicated Ed25519 JWT verifier can run. The handler still verifies every request. Keep `ACCOUNT_NATIVE_LEDGER_QUALIFIED` off until the native authority producer is independently qualified. Owner configuration requires exact HTTPS issuer, exact machine subject, the PUBLIC Ed25519 JWK, and a separate signed PostgREST `ACCOUNT_NATIVE_LEDGER_DATABASE_TOKEN` for `codevalanche_native_ledger_ingest_worker`. This worker does not request Auth admin credentials and cannot provision producers or read receipt/Auth tables. The owner alone supplies a matching producer qualification row (issuer, subject, SHA256 of decoded public `x`, current native generation); its default is unqualified. Rotate/revoke that row and generation with the signer. No client endpoint or ordinary account admin can enable qualification.

A signed native receipt binds canonical user/session/run/project/final outcome/time plus current consent, native generation, and policy version. Signatures last at most 60 seconds; SQL rechecks their expiry under current-state locks before insertion. Only a qualified native authority may attest trusted final execution; browser labels and host-reported remote receipts remain unconfirmed. The producer must keep its signer server-side and prove its execution-to-receipt binding before owner activation. No signer has been configured here. Ingestion deduplicates exact receipts and refuses conflicting receipt bodies or a second receipt for the same user/project/run. Success, failure, and cancellation are counted separately from this verified population; absent qualification remains null, with incomplete population coverage explicit. Consent withdrawal rejects old generations. Receipt metadata has 90-day retention and cascades when account-state erasure completes; no prompt, output, file path, provider token, or cost is collected.

Auth operation correlation is an opt-in application transaction protocol. `ACCOUNT_AUTH_CORRELATION_QUALIFIED` and the owner-maintained `codevalanche_auth_correlation_config.qualified` default off. Qualification requires the deployed GoTrue admin update path to write the supplied app metadata and all ban effects in one database transaction, with no later unmarked mutation. The inspected upstream path is [adminUserUpdate](https://github.com/supabase/auth/blob/master/internal/api/admin.go); this is source evidence, not proof of the hosted version. Qualify the actual deployed version/transaction shape, namespace, trigger privileges and crash behavior before enabling it. Nothing here assumes provider idempotency or creates a fictitious provider receipt.

For a qualified marked attempt, SQL stores an immutable binding of operation/job user, attempt, action, policy version, suspension generation and canonical deadline before Auth I/O. The worker sends that binding in `app_metadata.codevalanche_operation_v1`. ALWAYS triggers validate the current intent under shared transaction locks, enforce its absolute ban deadline, and create the application receipt in the same Auth transaction at commit. The temporary marker is removed in that transaction; unrelated Auth updates remain unaffected. A committed receipt proves only that exact Auth transaction committed; it does not prove mail delivery, native execution, or that the intent still authorizes current application access. Settlement separately rechecks actor membership and current target generation/policy, and cannot invent success from a worker boolean.

A lost HTTP response after commit is resolved from this receipt. On a fresh claim, a prepared attempt without a receipt can be atomically fenced under the same locks used by the Auth guard before a new attempt is issued. The fence prevents that old marked request from committing now or later; it is an application enforcement guarantee, not a timeout inference. A stale worker continuation cannot record or settle the replacement claim. Disabled/missing triggers or absent qualification refuse dispatch/fencing. Customer roles cannot provision qualification, read attempts or invoke the RPCs.

Unmarked legacy requests remain indeterminate: enabling this protocol cannot retrospectively fence or correlate them, and an Auth user/status read cannot prove their completion or cancellation. They still need an independently qualified correlated provider receipt or controlled operator reconciliation that establishes the old request cannot subsequently mutate Auth. Do not manually change a journal to confirmed/rejected merely to clear pending. The new local probes use a synthetic Auth transaction/HTTP provider and actual PostgreSQL, non-superuser Auth role, and Supabase SDK; real GoTrue qualification remains an owner gate. The normal legacy HTTP path now requires a correlated target-user response and compatible ban result, never an empty `error:null` acknowledgement. An unban response may omit `banned_until`, matching the provider's nullable JSON field.
Canonical account-project metadata is registered through authenticated v2 `project.binding.register {localAlias}` and read by `project.binding.get {projectId}` or `{localAlias}`. Alias is an opaque local identity ID; no paths, content, titles or qualification flags are accepted. PostgreSQL assigns stable `prj_` IDs uniquely per canonical Auth UUID/alias. Owner comes from the verified access token/current original session, with policy, provider ban, primary-auth/nonrecovery and session withdrawal rechecked under SQL locks. A foreign/missing project lookup is uniformly404. There is no project delete/update/list or owner override endpoint; account-state erasure cascades this metadata, without touching local files.

A binding proves `ownership:account_metadata` only. It has no physical workspace/root pin, native execution or producer qualification. Native admission must join its actual physically pinned local workspace alias and original actor/session to a fresh authenticated binding response; never promote workspaceId, a renderer label or current B account into missing original authority. Neither registration nor lookup opts into analytics or enables any producer/Internet/Run flag. Binding IDs and versions are immutable metadata, not remote grants.

The separate `codevalanche_native_project_ownership` read RPC is granted only to `codevalanche_native_ledger_ingest_worker`, never service_role/customer roles. It checks exact registered owner/project/binding version plus current original Auth session, consent generation and active current policy. Semantic denial returns owned:false; unexpected SQL/schema/transport errors propagate rather than masquerading as a valid owner. This delta does not change migration021 ingestion or retroqualify legacy opaque project IDs/receipts. Before implementing qualified delivery, separately review an atomic ownership check for the new registered binding namespace at ingest and its physical/admission join. Default producer qualification remains off.
