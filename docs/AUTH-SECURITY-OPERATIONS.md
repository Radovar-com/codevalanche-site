# Account security qualification

The additive v2 code is local implementation. Before rollout, the operator must provide separate staging receipts for database privileges, current Auth schema, OAuth clients and `aal2`/`amr` propagation, direct provider endpoints, CAPTCHA, SMTP, and recovery in another browser. No production changes are made by these scripts.

`supabase/scripts/auth-policy.json` is desired configuration, not a provider snapshot. Run `verify-auth-policy.mjs` on a sanitized actual snapshot; its output contains missing controls only. Recovery expiry is 900 seconds, new passwords at least 15 Unicode characters, exact HTTPS callbacks, distinct desktop/iOS/Android clients, and provider CAPTCHA. A frontend challenge or gateway rate limit cannot protect direct Auth requests. Keep refresh capacity separate from password ceilings. Failed password attempts never suspend accounts or revoke legitimate sessions.

Provider MFA/password verification hooks may require a plan capability. Do not purchase or enable them automatically. Record missing capability in the coverage report. No hook inference can substitute for successful provider session creation.

Recovery uses provider `verifyOtp({type:'recovery',token_hash})` with explicit exchange after navigation; remove callback secrets from history before network exchange. Email template must send to the exact account route with `token_hash`/`type`. Keep PKCE for ordinary OAuth/code callbacks. Qualify link expiry, reuse, mail scanner prefetch, and different browsers with actual staging email. Never log callback URLs, OTP codes, passwords, tokens or bodies. Configure production SMTP and prove actual delivery separately.

`auth.users` password changes and `auth.mfa_factors` changes update a server credential stamp and policy version through restricted triggers. Password changes withdraw existing application sessions. Recovery does not clear suspension or grant remote authority. OTP/invite/signup/magic-link sessions are conservatively restricted until fresh password/OAuth authentication because provider AMR does not reliably distinguish recovery OTP. This also restricts ordinary passwordless sessions; expand only after provider qualification establishes an authoritative recovery-purpose binding.

MFA freshness uses the verified MFA `amr.timestamp`, current verified factor count, and the provider change stamp; refresh `iat` is never freshness evidence. A factor change at the same second as verification requires a later challenge. Missing evidence denies sensitive actions. Direct provider factor changes must be tested in staging. Lost factors require an alternate verified factor or an operator-reviewed recovery process; access to email alone cannot remove MFA. Guest local remains available.

Rollback disables new online/remote admissions, keeps the additive schema, and preserves local data. No worker is scheduled or production configuration changed by these files.

Application migration never merges Keycloak/Supabase cohorts or canonical user UUIDs by email. This is distinct from provider identity linking: Supabase can automatically attach an OAuth identity with a matching verified email to the same Auth user UUID. The manual-linking setting does not disable automatic provider linking. Do not delete identities or add speculative hooks to change that behavior. Staging qualification must cover matching verified/unverified emails, existing password plus Google, Google-only password setup, and recovery after linking. Sign-in methods shown by the UI come from current provider identities. [Provider identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).

Temporary bans carry a monotonic suspension generation. Expiry jobs compare that generation and canonical deadline before completing; old jobs cannot relax a later ban. The worker reads authoritative current Auth ban status and never sends an old timed-expiry `ban_duration:none`, avoiding a delayed unban overwriting a newer provider ban. Provider outage or an active provider ban leaves expiry pending. Completion increments policy version and retains session/grant withdrawal. Due expiry is reconciled on verified account-policy reads and through the maintenance worker; the owner must qualify its schedule and alerts before release.

Maintenance source is `account-maintenance-dispatcher`, with a closed PostgreSQL due-job selector and at most 10 jobs per invocation. Existing operation/erasure/outbox leases prevent concurrent claim, and retry selection respects backoff and delivery deadlines. No variable UUID is needed in the scheduler request. `ACCOUNT_DISPATCHER_ENABLED` defaults off; erasure needs its separate qualification flag. The operator configures an authenticated HTTPS POST every 15–60 seconds and a separate daily retention call, then records successful retry/crash, pending/dead-letter alert and provider receipts. `verify-maintenance-config.mjs` checks a sanitized actual configuration receipt; it does not configure the scheduler or turn desired settings into proof.

Worker database roles are NOLOGIN and receive only their necessary EXECUTE capabilities. The selector has its own reader role, and each dispatched task uses a separate role-token adapter. PostgREST must verify the owner-supplied signed worker token and its role; the adapter checks an invoker capability RPC and refuses role mismatch. It never falls back to service_role. The owner configures these tokens, their lifetime and rotation; this code does not mint or inspect signing keys. Notifier, audit importer and retention use only a public API key plus their worker Authorization token and never request an Auth admin credential. Ban reconciliation and Auth erasure necessarily use a separate server-only Auth admin key: Supabase's Auth admin credential remains broad at the provider, so process isolation and endpoint capability checks are required. A JavaScript role variable cannot restrict that provider key.

If a separately suspended user cannot get a fresh provider session, self cancellation is not claimed reachable. `admin.deletion.cancel` offers an audited owner/accounts_admin path with verified current session, MFA within five minutes, reason and bound operation ID before purge. Cancellation restores the separate suspension; it never unbans the user or restores withdrawn grants. The self route still requires exact getUser validation, current session membership, recent primary authentication and enrolled MFA. Qualify banned-user recovery/login behavior in staging instead of bypassing provider checks.

Factor verification may update the provider stamp during the same second as the AMR claim. The server deliberately refuses that token for sensitive access rather than rounding the stamp down. First enrollment tells the user to perform a distinct later verification with a new code. SQL + principal/assurance boundary tests cover same-second refusal and later verified challenge; actual GoTrue ordering and OAuth propagation remain staging gates.
