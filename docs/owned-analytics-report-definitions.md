# Owned analytics report definitions and retention

Definition version: **1**. Canonical metric IDs and units are exported by `supabase/functions/_shared/metricDefinitions.ts`; strict report/query schemas live under `supabase/contracts/website-analytics/v1/`.

## Private API and populations

`GET /functions/v1/website-analytics/v1/reports/{overview|acquisition|pages|sections|journeys|downloads|accounts|quality|health}?query=<encoded JSON>` authenticates a current P3 operator, membership, session and required MFA before invoking service-only SQL. `apikey` alone is insufficient. SQL rechecks membership. No identifying evidence is returned in report rows.

`ReportQuery.accountMode` is optional and only legal on accounts: `outcomes` (default) retains the T7 account adapter; `activity` reads trusted `event_source=A`. All other browser views read W only. Operational outcomes, browser observations, and authenticated account activity never share a conversion denominator. Downloads display separate operational gateway/provider evidence with explicit source/filter limitations.

All periods are half-open UTC instants, displayed/grouped in the requested IANA zone. UTC and Europe/Bucharest have tested 23h/25h local days. Queries permit day/week, at most400days,3filters/10values each, limit100(default)/200(max), and opaque offset cursors. Arbitrary groupBy/comparison are currently rejected; callers may compute clearly scoped comparisons using two independent authorized reads with matching definitions/populations. Unsupported requests are never silently broadened.

Supported W filters, where the view allows them: pageId, sectionId, ctaId, acquisitionSource, campaign, deviceClass, osFamily, browserFamily, platform, releaseId, trafficClass. Account activity and health do not support filters. Country/appVersion/channel have no qualified captured context and are rejected. Operational account segmentation remains the T7 limitation. D redirects support only platform/releaseId; provider counters only releaseId. Unsupported source-specific scope produces null/unsupported_window for that metric. Known classified internal/test/suspected-bot rows are excluded by default; this is not proof of bot detection or human traffic.

## Metrics and grain

- `page_views`: earliest site/page-instance page_viewed observation, ordered by event_at/event_id before interval and dimensional filtering. Later duplicate observations never become a new view when the canonical raw row expires. `sessions`: distinct site/session IDs with eligible observations. Reloads repeating session_started are not new sessions.
- `browser_ids`: distinct site/browser IDs in the selected raw interval, not people or cross-domain identities. Browser/session counts and daily browser IDs use all eligible event-deduplicated observations, including later observations of an already-counted page instance; canonical page selection applies only to page-view counts and page-based eligibility. `repeat_browser_ids`: those IDs appearing in two or more distinct sessions inside that same interval; not lifetime new/returning visitors or D1/D7/D30 retention.
- `active_ms`/`account_active_ms`: nonnegative differences of canonical cumulative page revisions, assigned to observation time. Earlier retained revisions provide the baseline. This is an estimate: sampling intervals can straddle boundaries, missing earlier baselines limit accuracy, and there is no claim of exact wall-clock activity inside arbitrary endpoints. Revisions replace/difference prior cumulative values rather than summing lifetime totals.
- Acquisition chooses the earliest retained qualified campaign/referrer session-start snapshot, then event_at/event_id, preferring it over unknown reload snapshots. Events inherit that chosen session context. No retroactive Guest/account or cross-site person merge.
- `section_exposed_views`, `section_cta_after_exposure_views`, `section_reach`: page-instance/section grain. `PAGE_SECTION_SCOPE` in metricDefinitions.ts records actual site/page applicability; each eligible page contributes an opportunity for each applicable requested section, including sections with zero exposure. Unknown applicability is unsupported. A strict later CTA in the same exposed page/section qualifies; a fast click preceding exposure never does. Section/CTA filters preserve the eligible page denominator. Multiple sections are separate opportunities, not unique page views.
- `download_click_session_rate`: same-session page_viewed before download_clicked. Platform and CTA filters qualify the download target; eligible page-observed sessions remain the denominator. `signup_completion_rate` and `retention_d7` remain null without a qualified matched population/cohort implementation.
- `LCP_p75`, `INP_p75`, `CLS_p75`: nearest-rank p75 of latest metric-ID revisions, with per-row sampleSize and null when no sample. `javascript_errors` counts normalized observations. No private stack/form/URL capture.
- Activity IDs: `account_page_views`, `profile_edit_starts`, `profile_save_submissions`, `logout_clicks`, `account_active_ms`. Actual source currently instruments the profile surface and page engagement. These are observations/intents, not proof that profile persistence or logout succeeded. Activity rows keep the accounts row layout with concepts account_page_viewed/profile_edit_started/profile_save_submitted/logout_clicked/page_engagement_reported; engagement row count is canonical observed pages, while its metric is milliseconds. Provider coverage is empty.
- Default operational accounts use existing T7 concept IDs, provider capability and retained Auth sources. Missing provider audit/password-hook configuration is not_configured. Account creation/email verification describe retained accounts, excluding erased accounts. UUID profile results are mutable terminal actor/request outcomes: a successful retry replaces a failure and moves its timestamp. Profiles have no exact13month terminal archive; a requested window crossing raw90d returns unsupported_window for profile metrics. Legacy null-UUID outcomes are uncorrelated attempts. Exact attribution is success-only and never retrofits later opt-in.
- `download_redirects`: gateway request evidence, including direct requests and retries, not unique people/files. `provider_count_delta`: consecutive observed snapshot intervals, never actual transfer timestamps/completed files. Baseline/reset/removal or an interval crossing the requested start yields null. Nullable provider source watermark remains unknown freshness, never replaced by observed_at or carried ordering high-water. transfer_served/first_observed_opens/activations remain null without qualified producers; Guest activation unmeasured.

## History and execution

Refresh caches numeric active/visible revision contributions and the canonical-page decision on existing W raw rows before cleanup. These facts expire with those same 90-day rows; no identifying keys enter the 13-month archive. The earliest retained cached contribution preserves the expired cumulative baseline, including replacement and late intermediate revisions. Repeated refresh/prune keeps known totals stable after the predecessor expires.

002 adds a service-only evidence RPC returning one complete aggregate JSON envelope (not capped PostgREST row pages), W daily rollup refresh, source coverage and rollup-job coverage. Raw detail is restricted to90days. Stored W additive counts and daily distincts retain13calendar months in UTC and Europe/Bucharest. Archive reporting requires recorded job coverage, supported full calendar-day endpoints and current retained history. No job/coverage means null, not zero. Period browser/session distincts, repeat visitors and ordered funnels become unsupported after raw cleanup. Daily anonymous IDs are never summed into period uniques. Unfiltered historical daily overview rows retain daily starts/views/IDs; filtered historical totals are available where supported, without pretending to reconstruct missing distinct rows. Historical week/distinct and acquisition detail remain unsupported.

003 provides `wa_prune_website_analytics(p_now)` and `runWebsiteAnalyticsRetention(service, now)`. The job takes one transaction lock, refreshes W archives, deletes raw events/sessions strictly older90days, seals partially expired boundary days against later destructive recomputation, prunes additive archives/health at13months and expired ephemeral rate keys, then invokes later004/005 cleanup dynamically when available. W refresh reconciles current retained source, including late arrivals/cumulative revisions. It never append-sums mutable operational profile outcomes. The shared job is idempotent and server-callable; **T12 must schedule it**. No laptop job, scheduler or deployment was created here.

Receipt registry lifetime is separate: receipts expire in at most180days; expired/revoked rows are removed once retained raw/session references are gone. Account receipt bindings then cascade. This can retain an expired receipt for the remaining raw-reference window; it is not a blanket90day registry policy. Account P4/functional idempotency retention stays independent. Authoritative absence after physical receipt deletion returns an idempotent revocation ACK with next generation in a valid site scope; existing wrong site/proof/generation still fails. Database failure is never treated as absence. Browser stop/no-ID-revival semantics are unchanged.

Fresh migration order is001→002→003→004→005. 002/003 definitions require neither004 nor005; download/profile calls are runtime-deferred. Local PGlite tests cover the complete fresh chain, raw/archive parity,1501rows, scoped filters, pruning and privilege gates. Real hosted concurrency/provider freshness, scheduling and activation are T12 qualifications. Public capture remains OFF.

## Qualified provider session metadata (migrations 007, 008, 011)

The V1 `login_succeeded` meaning remains provider-authenticated session issuance. The independent `provider_session_metadata` source supports prospective password sessions and native social OAuth sessions with a canonical Auth user/session and persisted primary AMR exactly `password` or `oauth`, excluding recovery. AAL1 consumer sessions count. MFA completion and application/operator admission are distinct unmeasured concepts; the operator report still requires current AAL2 and strict credential evidence. Delegated `oauth_provider`/`authorization_code` grants and recovery/OTP/magic-link/invite/signup/TOTP-only sessions are excluded; this is not a count of all OAuth client activity.

Deferred provider-table INSERT observations create one receipt per canonical session UUID, including when the session and primary AMR arrive in separate transactions. Only the provider database role may produce receipts. The source never reads browser callbacks or backfills the legacy 009 security rows. Existing `provider_audit_enabled` and password-hook flags remain independent. The report chooses only this producer for login, even if audit is later enabled, so audit/session identities cannot double count. Other concepts retain their original source requirements.

Qualification defaults false and must follow actual positive/negative GoTrue canaries. The read-only qualifier checks the capture function, exact deferred INSERT trigger OIDs/type/attributes/origin mode, relevant schema types and provider ownership, reachable role permissions and replication defaults. It is a current metadata check, not proof of uninterrupted historical coverage. Health failures disable qualification when health persistence succeeds. Capture errors are contained so operational Auth still commits; simultaneous receipt and health-store failure can be invisible. Coverage therefore always remains partial.

The per-concept watermark is the last successfully persisted receipt observation, never report generation time. Installation/raw-retention boundaries appear in the login capability. Entirely earlier periods and periods after the last observed watermark are null/unmeasured; overlapping windows show only retained prospective counts with partial coverage. No unsupported history is represented as a measured zero. Raw receipt retention is 90 days through the existing prune entrypoint. Logout/session deletion preserves the receipt, Auth-user erasure cascades, and no identifying 13-month archive is created. Source health and operator qualification must be rechecked after any provider upgrade.

Migration008 bounds each optional capture/health database lock wait to100ms through function-local lock_timeout, automatically restoring the caller's setting. Both capture and failure-marker handlers explicitly contain query_canceled (SQLSTATE57014) as well as ordinary exceptions, including execution at deferred transaction commit. The qualifier requires this exact timeout configuration; installation disables qualification for revalidation. This is a per-lock wait bound, not a total authentication latency guarantee. If a locked/unavailable health store also prevents recording the loss, coverage still remains partial; successful Auth does not imply successful analytics capture.

Migration011 adds native social OAuth capture with its own `oauth_observed_from` timestamp. Password history and the original source installation boundary remain intact. A session created before the social boundary cannot acquire a retrospective OAuth receipt from a later AMR notification. The report capability exposes the exact retained password/social boundaries; totals remain partial retained primary-session observations. Password takes priority when both supported methods exist at first capture. Repeated AMR, refresh or MFA notifications never change an existing canonical-session receipt. The qualifier also verifies the social boundary column type, non-null property and clock_timestamp default. Upgrade resets source qualification false.

The native `oauth` shape is supported by read-only existing Google-session metadata and controlled provider-role SQL tests. Neither is evidence that a new external Google sign-in has been captured after011. Staging Google authentication is unconfigured. After reviewed deployment, a real human Google sign-in must be independently checked for one prospective canonical-session receipt while the source remains disabled, before explicit source activation. No Google identity details, delegated grant counts or provider credentials belong in report DTOs.
