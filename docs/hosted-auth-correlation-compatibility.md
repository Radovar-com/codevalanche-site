# Hosted Auth correlation installation

Migration `202610110022_auth_operation_correlation.sql` was revised before its first qualified deployment after a fresh Supabase staging apply failed with SQLSTATE42501. The failed transaction left neither migration history nor correlation objects. This is an explicit exception to the earlier migration freeze: preserve the original historical snapshot and hash, identify this revised file separately, and leave the other28 original migration files unchanged. Never mark the failed migration applied or rewrite already-applied history.

Supabase retains ownership of `auth.users` under `supabase_auth_admin`. Its migration role may create triggers but cannot issue `ALTER TABLE ... ENABLE ALWAYS TRIGGER` on that managed table. The migration now preserves ALWAYS when executed by a legitimate owner/superuser and retains the ordinary enabled triggers created by `CREATE TRIGGER` only for the recognized managed owner. Unknown non-owned tables fail installation. No ownership changes, owner-role memberships or privilege escalation are performed.

The ordinary hosted mode qualifies only in origin/local execution, with exact trigger functions, event types, unconditional row firing and deferred commit properties. Required Auth columns, explicit qualification flag, expected managed ownership and all six expected Auth/application roles must exist. Those roles and their SET ROLE reachability must not allow changing `session_replication_role`; Auth must have no role memberships, and relevant database/role defaults must not select replica. Missing, disabled, replaced, conditional or replica-only triggers refuse qualification. The original transaction guard, receipt, stale-attempt fence, current policy/principal checks and P4 authority are unchanged.

Ordinary enabled triggers do **not** promise execution for arbitrary privileged replica writes. This mode relies on the managed Auth service executing ordinary origin/local transactions and on operators preserving its privilege/configuration boundary. ALWAYS remains the owner-controlled mode. A platform administrator able to alter the table or functions remains a trusted operator in either mode.

`qualified` remains false after installation. Actual hosted Auth transaction success, committed exact receipt, binding removal, stale/fenced refusal and rollback must be demonstrated on isolated synthetic identities before enabling correlated operations. Qualification needs a controlled canary interval because the guard itself requires the flag; restore false on any failed canary and keep public workers disabled throughout. Local PostgreSQL fixtures and SDK mocks do not establish hosted provider qualification. Recheck catalog/privilege evidence after provider upgrades or operator changes.
